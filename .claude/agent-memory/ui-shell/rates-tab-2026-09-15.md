Built 2026-09-15 in `ui/tabs/rates.py`, wired into `ui/tabs/blotter.py`'s "rates"
sub-tab (was a placeholder; see [[blotter-subtabs-2026-09-15]] /
[[blotter-futures-subtab-2026-09-15]] for the placeholder history). Trigger: a new
agent "rates-pricer" landed `engine/rates/` (QuantLib OIS bootstrap + swap pricer,
`bootstrap_and_store`/`price_and_store`) and `data/ingest/schema.py`'s
`OFFICIAL_MARK_SOURCE` now maps `PAR_RATE`/`PV_USD`/`DV01_USD` to `QL_PRICER`
(official), demoting `BBG_BDH` to reconciliation-only for those three mark_types.

**Why bypass `blotter_pricing.priced_value_book`**: that pipeline only ever builds
FX/FUTURE rows (documented in its own and `blotter.py`'s docstrings) — extending it to
IRS was out of scope and out of my directory (engine/pnl is pnl-engine's). So
`ui/tabs/rates.py` reads `trades`/`instruments`/`marks_official` directly: one row per
IRS trade, direction from `quantity` sign (`>0` = pay fixed, per CLAUDE.md "Leg
layouts" and `engine/rates/store.py`'s own convention), PAR_RATE/PV_USD/DV01_USD from
`marks_official`, and a `recon_status` (OK/WARN/MISSING) comparing PV_USD against the
reconciliation-only `BBG_BDH` mark read straight from `marks` (never through
`marks_official`, which would return the QL_PRICER row instead and silently defeat the
comparison). Tolerance is home-grown (`max($1000, 0.5% of official PV)`) since no
recon-status convention existed anywhere else in the app to reuse — checked
`blotter.py` and `reconciliation.py` first, confirmed absent, documented the tolerance
choice inline in `rates.py`'s docstring.

**Wiring gotcha**: `blotter.py`'s per-scope P&L strip / row-click detail / filter-bar
callbacks are all generic over `SCOPE_ORDER` and assume a `priced_value_book`-shaped
table (`trade_id`/`mark`/`pnl_usd`/... columns, `derived_virtual_data`). The Rates
table has none of that shape, so it's excluded from that registration loop (alongside
"bundles") and uses its own table id `rates-datatable` (not
`blotter-datatable-rates`) to avoid any accidental collision. It has no strip, filter
bar or detail panel — just a table, rebuilt by the existing top-level `_update`
callback whenever the as-of date or sub-tab changes (that callback was already generic
enough to need zero changes).

Had to touch `tests/test_ui_blotter.py` (not just a new `tests/test_ui_rates.py`) to
retarget two tests that asserted the old "rates" placeholder wording — they now assert
on the "options" scope (still a placeholder) instead, plus one new test confirming
`scope_layout("rates", ...)` delegates to `ui.tabs.rates`.

Marks schema note for future IRS UI work: `engine/rates/store.py` writes
`PV_USD`/`DV01_USD`/`PAR_RATE` marks with `settle_date` = the FIXED leg's maturity
date, and CLAUDE.md confirms exactly one `instrument_id` per swap — so joining on
`(as_of_date, instrument_id)` alone (no `settle_date` needed) is safe for IRS, unlike
FX where the same pair can have many outstanding value dates.
